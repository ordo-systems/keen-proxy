# 0.9.0 — upgrading from 0.8.0

Version **0.9.0** expands connection support, adds native OpenWrt installation and updates, and strengthens build-time memory and secret checks. These notes cover the changes and migration steps from **0.8.0**.

[Version history](index.md) · [0.8.0 release](https://github.com/ordo-systems/keen-proxy/releases/tag/v0.8.0)

## Highlights

- Experimental **AmneziaWG 2/3** profiles and offline Amnezia `vpn://` import.
- **TrustTunnel embedded in the engine**, without a separate client process.
- Expanded **XHTTP, VLESS encryption, and REALITY** options.
- Pause **connections, groups, and individual rules** without deleting their settings.
- **Native OpenWrt installation, panel updates, and rollback** through procd; x86-64 and 32-bit x86 join the release build matrix.
- **Settings → System** for a process-wide soft Go memory recommendation; documented router minimum raised to **256 MiB RAM**.
- **Memory regression and AWG stress gates** before application builds, plus **secret scanning** for pull requests and `main` history.

## Connections and protocols

### AmneziaWG and offline import

[PR #25](https://github.com/ordo-systems/keen-proxy/pull/25) adds single-peer AWG 2/3 `.conf` profiles, editing through the shared draft/Apply workflow, and local import of standalone Amnezia `vpn://` client exports. Multiple exported profiles require an explicit choice. Unsupported fields, executable hooks, malformed data, and excessive junk-packet bursts are rejected rather than silently dropped.

The engine is pinned to **sing-box-lx 1.14.4-lx.35** with matching dependency forks. No kernel AWG module or separate AWG daemon is required. This is not subscription activation, server provisioning, or integration with an Amnezia service API. Imported profile DNS does not replace KeenProxy's DNS policy; application UDP still needs the existing TPROXY facilities.

### Embedded TrustTunnel, XHTTP, VLESS, and REALITY

[PR #32](https://github.com/ordo-systems/keen-proxy/pull/32) replaces the external TrustTunnel process and loopback-SOCKS bridge with the native engine outbound. Profiles use the complete exported `tt://` link. Supported legacy TrustTunnel configuration is migrated on load and saved in the link representation on Apply; unsupported historical options fail explicitly.

Both full and lite support XHTTP and native TrustTunnel. Supported link imports preserve VLESS encryption and REALITY key-share/TLS-fragmentation parameters. Advanced options are available through supported links or raw sing-box JSON, not a new manual form for every engine field. Invalid or conflicting parameters are rejected. XHTTP with Vision requires enabled VLESS encryption; TLS/REALITY alone does not satisfy that requirement.

| Build | Transport boundary |
| --- | --- |
| Full | Includes QUIC/HTTP/3. |
| Lite | Keeps the smaller protocol registry and TCP/TLS transports, including TrustTunnel over HTTP/2 and XHTTP over HTTP/1.1 or HTTP/2. HTTP/3 requests are rejected, not silently downgraded. |

Native TrustTunnel does not retain the external client's address-racing behavior: for same-port IP lists, it selects the first IPv4 in exported order, otherwise the first IP, without trying the remaining addresses on failure. With certificate verification enabled, custom SNI and the verification hostname must agree. See the [connection compatibility and migration guide](../user-guide.md#sing-box-lx-compatibility).

## Pause connections and rules

[PR #28](https://github.com/ordo-systems/keen-proxy/pull/28) adds activation controls for connections, groups, and individual domain, IP, country, and category rules. Settings remain available for later re-enabling. Disabling a parent does not erase the enabled/disabled choices of its children.

Changes still use the global draft and **Apply** action. Disabled tunnel targets use configured fallback behavior or block when no permitted route exists; disabling a connection does not implicitly authorize direct access. Parameter and diagnostic actions are separated, with activation controls available on desktop and narrow screens.

## Installation, platforms, and updates

[PR #27](https://github.com/ordo-systems/keen-proxy/pull/27) adds full/lite x86 binaries and native OpenWrt management across the six release architectures:

| Linux architecture | Release suffix | Requirement |
| --- | --- | --- |
| x86-64 | `amd64` | AMD64 v1 baseline; CPU vendor does not matter. |
| 32-bit x86 | `386` | SSE2; the name does not imply Intel 80386 compatibility. |
| ARM32 | `armv5` | ARMv5 or later, soft float. |
| ARM64 | `arm64` | AArch64. |
| MIPS little-endian | `mipsle` | Soft float. |
| MIPS big-endian | `mipsbe` | Soft float. |

- **Native OpenWrt:** `/usr/bin/keenproxy`, `/etc/keenproxy/config.yaml`, and `/etc/init.d/keenproxy` under procd, without Entware. Clean configuration uses `br-lan` and `/etc/keenproxy/token`; custom configuration is preserved. Release records and update preferences use persistent storage under `/usr/share/keenproxy/`, not volatile `/var`.
- **Entware:** existing `/opt` paths and service remain supported, now with architecture selection for all six release targets. An existing managed Entware installation on OpenWrt is not silently migrated to native paths.
- **Managed updates:** panel installation, scheduling, and rollback use verified downloads, candidate validation, operation locks, and failed-start recovery. Native transactions require the checksummed `keenproxy.openwrt` asset; a release without it cannot be a native installation or rollback target.
- **Access:** installation/CLI updates print the panel URL when it can be determined. The read-only `--url` and `--key` options retrieve configured access details without starting the daemon or rotating its token. Native installations must explicitly select `/etc/keenproxy/config.yaml` because CLI defaults remain Entware-oriented. Keep token output private.

The supported hardware floor is **256 MiB of total router RAM**, including lite, on OpenWrt and Keenetic/Netcraze. Reserve memory for firmware and other services and persistent storage for staging and rollback; the floor is not a workload-capacity guarantee.

This does not introduce a native firewall4/nftables backend. Compatible iptables tools, NAT/TPROXY kernel facilities, and testing on the target firmware remain necessary. The optional NDM callback from 0.8.0 remains specific to compatible Keenetic/Netcraze firmware; OpenWrt retains periodic watchdog recovery.

## System memory setting

**Settings → System** adds optional `system.memory_limit_mib`, applied at startup and through the shared **Apply** workflow. A memory-only change does not restart the service or engine.

Priority is: explicit configuration → startup Go memory limit, including `GOMEMLIMIT` → **768 MiB** when no startup limit was supplied. Explicit `GOMEMLIMIT=off` remains respected; clearing a configuration override restores the selected default mode.

This is a **soft Go recommendation for the whole KeenProxy process**, not a hard RSS cap. The 768 MiB fallback is not a minimum-RAM requirement and does not mean that memory is physically available on a 256 MiB router. Lower recommendations can increase GC/CPU work and reduce throughput. See [system memory settings](../user-guide.md#soft-memory-limit).

## Build-time memory checks

[PR #31](https://github.com/ordo-systems/keen-proxy/pull/31) adds two separate, fail-closed checks before normal application builds, CI, and release builds:

- **`make memory-regression`:** compare the full daemon with the fixed 0.8.0/pre-PR-#25 baseline under matched ordinary-WireGuard workloads. Three paired trials compare phase medians; increases above `max(10% of baseline, 8 MiB)` fail. AWG-only measurements are not compared with an old binary that cannot load AWG.
- **`make memory-stress`:** drive 32 continuous AWG TCP streams with verified progress and payloads. The measured daemon alone gets a **320 MiB Go budget**, while RSS and lifetime `VmHWM` must stay **below 384 MiB**. The separate test container uses **2 GiB RAM and two CPUs** and is not a router-capacity emulator.

Developers need Docker with privileged isolated-container support, Python, Git history, and the pinned Go toolchain for normal builds. Serial measurement phases alone take at least **5 minutes 21 seconds**, plus compilation and setup. Invalid evidence and cleanup failures block the build; a CI pass does not erase a contradictory local measurement.

These are test/build contracts, **not a production memory optimization, leak fix, 320 MiB runtime default, or proof that all workloads fit a 256 MiB router**. Host benchmarks do not certify sustained behavior on every architecture or complete post-load memory reclamation. See the [developer guide](https://github.com/ordo-systems/keen-proxy/blob/bc777ad2d5cd1cd228c4fc2899cc5b4a5d10d1cb/docs/en/development.md#memory-regression-gate).

## Secret scanning

[PR #34](https://github.com/ordo-systems/keen-proxy/pull/34) adds automated checks for credentials committed to Git:

- **Pull requests:** scan the commits introduced by the branch, from `base` to `head`.
- **`main`:** scan every commit reachable from `main`, not the history of other branches.
- **Local verification:** `make check-secrets` runs the same history scope as the `main` check.

The scanner uses the MIT-licensed **gitleaks 8.30.1** binary, pinned and verified by checksum, rather than the separately licensed GitHub Action. A clean result does not replace manual review of configuration and history, certify that all secrets have been found, or inspect configuration on a running router.

## Upgrade checklist and compatibility

1. **Select the release assets.** Use the 0.9.0 GitHub release and verify that the required files and checksums are present; a `main` checkout is not a substitute for a tagged binary release.
2. **Keep a recovery path.** Back up configuration and token files privately, keep the previous binary and pre-migration TrustTunnel configuration, and retain SSH/LAN access. Follow the [installation/update guide](../getting-started.md#install-or-update-from-github) or the [native OpenWrt guide](../getting-started.md#native-openwrt-installation).
3. **Review migrated connections before Apply.** Check AWG parameters, native TrustTunnel identity/endpoint behavior, and whether your chosen full/lite build supports the profile's transport. Imported DNS does not take over KeenProxy DNS ownership.
4. **Adapt external automation.** The status API no longer exposes the external-process `trusttunnel` field. `--trusttunnel-only` is removed; the historical `--without-trusttunnel` input remains accepted but no longer changes the payload.
5. **Do not delete old client files automatically.** Upgrade/uninstall leaves prefix-relative `bin/trusttunnel_client` and `share/keenproxy/trusttunnel/` untouched. Remove them manually only after confirming no other service or external-client rollback needs them; generated files can contain credentials.
6. **Verify the result.** Check panel access, connection health, representative client traffic, DNS behavior, and router memory. A successful HTTP probe does not prove HTTPS transfers or DNS-leak protection. Existing participant UDP/443 policy is unchanged.

Rollback keeps the existing configuration, which can be incompatible with an older engine. Preserve a pre-upgrade backup; migration to native TrustTunnel is not a promise of automatic reverse migration. Native OpenWrt cannot roll back through this installer to 0.8.0 because that release has no procd controller asset.
