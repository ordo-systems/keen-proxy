# 0.9.0 — обновление с 0.8.0

Версия **0.9.0** расширяет поддержку соединений, добавляет нативную установку и обновление OpenWrt, а также усиливает проверки памяти при сборке и поиск секретов. Эти заметки описывают изменения и порядок перехода с **0.8.0**.

[История версий](index.md) · [Релиз 0.8.0](https://github.com/ordo-systems/keen-proxy/releases/tag/v0.8.0)

## Главное

- Экспериментальные профили **AmneziaWG 2/3** и офлайн-импорт Amnezia `vpn://`.
- **TrustTunnel встроен в движок**, отдельный клиентский процесс больше не нужен.
- Расширены параметры **XHTTP, шифрования VLESS и REALITY**.
- Можно отключать **соединения, группы и отдельные правила**, не удаляя настройки.
- **Нативная установка OpenWrt, обновление и откат из панели** через procd; в матрицу сборок добавлены x86-64 и 32-битная x86.
- Раздел **Настройки → Система** для мягкой рекомендации Go по памяти всего процесса; аппаратный минимум в документации повышен до **256 МиБ RAM**.
- **Проверки регрессий памяти и стресс-тест AWG** перед сборкой приложения, а также **поиск секретов** в pull request и истории `main`.

## Соединения и протоколы

### AmneziaWG и офлайн-импорт

[PR #25](https://github.com/ordo-systems/keen-proxy/pull/25) добавляет однопировые профили AWG 2/3 `.conf`, редактирование через общий черновик и применение, а также локальный импорт самостоятельных клиентских экспортов Amnezia `vpn://`. Если в экспорте несколько профилей, нужно выбрать один явно. Неподдерживаемые поля, исполняемые хуки, некорректные данные и чрезмерные серии мусорных пакетов отклоняются, а не отбрасываются молча.

Движок закреплён на **sing-box-lx 1.14.4-lx.35** вместе с соответствующими форками зависимостей. Модуль AWG в ядре и отдельный демон AWG не нужны. Это не активация подписок, настройка сервера или интеграция с API сервиса Amnezia. DNS из профиля не заменяет политику DNS KeenProxy; для UDP приложений по-прежнему нужна поддержка TPROXY.

### Встроенный TrustTunnel, XHTTP, VLESS и REALITY

[PR #32](https://github.com/ordo-systems/keen-proxy/pull/32) заменяет внешний процесс TrustTunnel и локальный SOCKS-мост нативным outbound движка. Профили используют полную экспортированную ссылку `tt://`. Поддерживаемая старая конфигурация TrustTunnel преобразуется при загрузке и сохраняется в виде ссылки при применении; неподдерживаемые старые параметры явно отклоняются.

Обе сборки, full и lite, поддерживают XHTTP и встроенный TrustTunnel. При импорте поддерживаемых ссылок сохраняются параметры шифрования VLESS, обмена ключами REALITY и фрагментации TLS. Расширенные параметры доступны через поддерживаемые ссылки или raw sing-box JSON, а не через отдельную ручную форму для каждого поля движка. Некорректные и конфликтующие параметры отклоняются. Для XHTTP с Vision нужно включённое шифрование VLESS; одного TLS/REALITY недостаточно.

| Сборка | Поддержка транспортов |
| --- | --- |
| Full | Включает QUIC/HTTP/3. |
| Lite | Сохраняет сокращённый реестр протоколов и транспорты TCP/TLS, в том числе TrustTunnel через HTTP/2 и XHTTP через HTTP/1.1 или HTTP/2. Запросы HTTP/3 отклоняются без незаметного понижения транспорта. |

Встроенный TrustTunnel не сохраняет параллельный выбор адресов внешнего клиента: из списка IP с одинаковым портом выбирается первый IPv4 в порядке экспорта, иначе первый IP; остальные адреса при ошибке не перебираются. При включённой проверке сертификата custom SNI должен соответствовать имени, по которому проверяется сертификат. См. [совместимость соединений и миграцию](../user-guide.md#sing-box-lx-compatibility).

## Отключение соединений и правил

[PR #28](https://github.com/ordo-systems/keen-proxy/pull/28) добавляет управление активностью соединений, групп и отдельных правил доменов, IP, стран и категорий. Настройки сохраняются для последующего включения. Отключение родителя не стирает выбранное состояние его дочерних правил.

Изменения по-прежнему проходят через общий черновик и кнопку **Применить**. Для отключённого туннеля используется настроенное резервирование либо блокировка, если разрешённого маршрута нет; отключение соединения само по себе не разрешает прямой выход. Действия с параметрами отделены от диагностики; управление активностью доступно на компьютере и узком экране.

## Установка, платформы и обновление

[PR #27](https://github.com/ordo-systems/keen-proxy/pull/27) добавляет full/lite-бинарники x86 и нативное управление OpenWrt для шести архитектур релиза:

| Архитектура Linux | Суффикс сборки | Требование |
| --- | --- | --- |
| x86-64 | `amd64` | Базовый уровень AMD64 v1; производитель CPU не важен. |
| 32-битная x86 | `386` | SSE2; название не означает совместимость с Intel 80386. |
| ARM32 | `armv5` | ARMv5 и новее, soft float. |
| ARM64 | `arm64` | AArch64. |
| MIPS little-endian | `mipsle` | Soft float. |
| MIPS big-endian | `mipsbe` | Soft float. |

- **Нативный OpenWrt:** `/usr/bin/keenproxy`, `/etc/keenproxy/config.yaml` и `/etc/init.d/keenproxy` под управлением procd, без Entware. Начальная конфигурация использует `br-lan` и `/etc/keenproxy/token`; пользовательская конфигурация сохраняется. Запись о релизе и настройки обновления хранятся постоянно в `/usr/share/keenproxy/`, а не в непостоянном `/var`.
- **Entware:** сохраняются существующие пути `/opt` и служба; выбор архитектуры теперь охватывает все шесть целей релиза. Существующая установка под управлением Entware на OpenWrt не переносится на нативные пути автоматически.
- **Управляемое обновление:** установка, расписание и откат из панели используют проверенные загрузки, валидацию новой конфигурации, блокировки операций и восстановление при неудачном запуске. Для нативных транзакций нужен файл `keenproxy.openwrt` с контрольной суммой; релиз без него не подходит для нативной установки и отката.
- **Доступ:** после установки и обновления из CLI выводится URL панели, если его удалось определить. Команды только для чтения `--url` и `--key` получают настроенные параметры доступа без запуска демона и смены токена. Для нативной установки нужно явно указать `/etc/keenproxy/config.yaml`: пути CLI по умолчанию остаются ориентированными на Entware. Не публикуйте вывод токена.

Нижняя граница аппаратных требований — **256 МиБ общей памяти роутера**, в том числе для lite, на OpenWrt и Keenetic/Netcraze. Оставьте запас памяти для прошивки и других служб, а также место на постоянном разделе для новой сборки и отката; этот минимум не гарантирует работу любой нагрузки.

Нативный backend firewall4/nftables не добавляется. По-прежнему нужны совместимые утилиты iptables, поддержка NAT/TPROXY в ядре и проверка на целевой прошивке. Необязательный callback NDM из 0.8.0 остаётся специфичным для совместимых прошивок Keenetic/Netcraze; OpenWrt использует периодическое восстановление сторожем.

## Настройка памяти системы

В **Настройки → Система** появился необязательный параметр `system.memory_limit_mib`, применяемый при запуске и через общий процесс **Применить**. Изменение только памяти не перезапускает службу или движок.

Приоритет: явная конфигурация → лимит Go при запуске, включая `GOMEMLIMIT` → **768 МиБ**, если стартовый лимит не задан. Явный `GOMEMLIMIT=off` учитывается; очистка переопределения в конфигурации возвращает выбранный режим по умолчанию.

Это **мягкая рекомендация Go для всего процесса KeenProxy**, а не жёсткий предел RSS. Резервное значение 768 МиБ не является минимальным требованием к RAM и не означает, что столько памяти физически доступно на роутере с 256 МиБ. Более низкие значения могут увеличить работу GC/CPU и снизить пропускную способность. См. [мягкий лимит памяти](../user-guide.md#soft-memory-limit).

## Проверки памяти при сборке

[PR #31](https://github.com/ordo-systems/keen-proxy/pull/31) добавляет две раздельные обязательные проверки перед обычной сборкой приложения, CI и сборкой релиза:

- **`make memory-regression`:** сравнение полного демона с закреплённой базой 0.8.0/до PR #25 на одинаковой нагрузке обычного WireGuard. Сравниваются медианы фаз трёх парных прогонов; превышение `max(10% of baseline, 8 MiB)` приводит к отказу. Замеры только AWG не сравниваются со старым бинарником, который не умеет загружать AWG.
- **`make memory-stress`:** нагрузка из 32 непрерывных TCP-потоков AWG с проверкой прогресса и содержимого. Только измеряемый демон получает **рекомендацию Go в 320 МиБ**, а RSS и пиковый за время жизни `VmHWM` должны оставаться **ниже 384 МиБ**. Отдельный тестовый контейнер использует **2 ГиБ RAM и два CPU** и не эмулирует вместимость памяти роутера.

Для обычных сборок разработчикам нужны Docker с поддержкой привилегированных изолированных контейнеров, Python, история Git и закреплённый Go toolchain. Только последовательные фазы измерений занимают не менее **5 минут 21 секунды**, не считая компиляции и подготовки. Некорректные данные и ошибки очистки блокируют сборку; успешный CI не отменяет противоречащий ему локальный замер.

Это контракт тестирования и сборки, **а не оптимизация памяти приложения, исправление утечки, стартовый лимит в 320 МиБ или доказательство работы любой нагрузки на роутере с 256 МиБ**. Замеры на хосте не подтверждают длительную стабильность на всех архитектурах или полный возврат памяти после нагрузки. См. [руководство разработчика](https://github.com/ordo-systems/keen-proxy/blob/bc777ad2d5cd1cd228c4fc2899cc5b4a5d10d1cb/docs/ru/development.md#проверка-регрессий-памяти).

## Поиск секретов

[PR #34](https://github.com/ordo-systems/keen-proxy/pull/34) добавляет автоматическую проверку учётных данных, попавших в Git:

- **Pull request:** проверяются коммиты, добавленные веткой, от `base` до `head`.
- **`main`:** проверяется каждый коммит, достижимый из `main`, а не история остальных веток.
- **Локальная проверка:** `make check-secrets` проверяет тот же диапазон истории, что и проверка `main`.

Используется бинарник **gitleaks 8.30.1** с лицензией MIT, закреплённый и проверяемый по контрольной сумме, а не отдельно лицензируемый GitHub Action. Успешная проверка не заменяет ручной просмотр конфигурации и истории, не гарантирует обнаружение всех секретов и не проверяет настройки работающего роутера.

## Порядок обновления и совместимость

1. **Выберите файлы релиза.** Используйте релиз 0.9.0 в GitHub и проверьте наличие нужных файлов и контрольных сумм; копия `main` не заменяет бинарный выпуск по тегу.
2. **Сохраните путь восстановления.** Сделайте приватные резервные копии конфигурации и токена, сохраните предыдущий бинарник и конфигурацию TrustTunnel до миграции, оставьте доступ по SSH/LAN. Следуйте [инструкции по установке и обновлению](../getting-started.md#install-or-update-from-github) или [инструкции нативного OpenWrt](../getting-started.md#native-openwrt-installation).
3. **Проверьте мигрированные соединения до применения.** Сверьте параметры AWG, идентичность и выбор адреса нативного TrustTunnel, а также поддержку транспорта выбранной сборкой full/lite. DNS из импорта не перехватывает управление DNS KeenProxy.
4. **Адаптируйте внешнюю автоматизацию.** В status API больше нет поля внешнего процесса `trusttunnel`. Режим `--trusttunnel-only` удалён; исторический аргумент `--without-trusttunnel` принимается, но больше не меняет состав установки.
5. **Не удаляйте старые клиентские файлы автоматически.** Обновление и удаление оставляют `bin/trusttunnel_client` и `share/keenproxy/trusttunnel/` относительно префикса установки. Удаляйте их вручную только после проверки, что они не нужны другой службе или откату на внешний клиент; сгенерированные файлы могут содержать учётные данные.
6. **Проверьте результат.** Проверьте доступ к панели, состояние соединений, характерный клиентский трафик, DNS и память роутера. Успешный HTTP-запрос не подтверждает работу HTTPS-передач или отсутствие утечек DNS. Существующая политика UDP/443 для участников не меняется.

При откате сохраняется текущая конфигурация, которая может оказаться несовместимой со старым движком. Сохраните резервную копию до обновления: миграция на встроенный TrustTunnel не обещает автоматического обратного преобразования. Через нативный установщик OpenWrt нельзя откатиться на 0.8.0: в том релизе нет файла службы procd.
